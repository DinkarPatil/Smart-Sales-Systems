# Smart Sales Systems — Architecture Documentation

## 1. Project Overview

**Smart Sales Systems** (a.k.a. *Sales RAG Chatbot System*) is a full-stack, multi-tenant sales support platform. Customer complaints/queries are funneled in through a Google Forms webhook, an initial answer is generated by a Retrieval-Augmented Generation (RAG) pipeline grounded in each company's product manuals, and the conversation is then routed to Sales Representatives, escalated to Owners, or monitored by Managers and a global Admin — all under a strict Role-Based Access Control (RBAC) model.

- **Backend:** FastAPI (async), SQLAlchemy 2.x async ORM, SQLite (`aiosqlite`), JWT auth, LlamaIndex + Groq (Llama-3-70B) for RAG, Resend for transactional email, PyMuPDF + Ollama VLM for PDF/image OCR.
- **Frontend:** React 18 (Vite), Tailwind CSS, Framer Motion, Lucide Icons, Recharts, Axios, React Router v6.

## 4. Roles & RBAC

Four roles, persisted as plain strings in `users.role` (enum `UserRole` in [models.py:8](../backend/app/models/models.py#L8)):

```
Admin  ←  global, no company scope
Owner  ←  one-company, top-of-tenant
Manager←  one-company, mid-management
SalesRep← one-company, individual contributor
```

Gating is performed in two places:
- **Backend:** chained FastAPI dependencies in [`api/deps.py`](../backend/app/api/endpoints/) — `get_current_user` → `get_current_active_user` → `get_current_active_admin / _owner / _manager / _sales_rep`. A wrong role yields **403** *"… clearance required"*.
- **Frontend:** [`App.jsx`](../frontend/src/App.jsx) inspects `user.role` and `<Navigate to="/login" />` on mismatch.

### 4.1 Admin role (deep-dive)

**Purpose:** super-user / platform operator. Admins are **not** scoped to a `company_id` — they see and govern every tenant.

**How an Admin is created (only two paths):**

1. **Self-registration with secret key** — `POST /api/v1/auth/register` carrying `admin_secret_key == settings.ADMIN_SECRET_KEY` ([core/config.py:13](../backend/app/core/config.py#L13)). Sets `role="Admin"`, `is_active=True`, dispatches an "Administrative Clearance Granted" email. Anyone with the secret key can mint themselves an Admin — keep this env var safe.
2. **Provisioned by an existing Admin** — `POST /api/v1/admin/users` with `role="Admin"`. Auto-active, credentials emailed to the new admin in plaintext.

There is currently **no** demote-admin / revoke-admin endpoint distinct from the generic `PUT /admin/users/{id}` (which can flip `role` and `is_active`).

**Admin permissions matrix:**

| Capability                                  | Endpoint                                              |
| ------------------------------------------- | ----------------------------------------------------- |
| Global statistics                           | `GET  /api/v1/admin/stats`                            |
| List every user (with company info)         | `GET  /api/v1/admin/users`                            |
| Provision a user of any role                | `POST /api/v1/admin/users`                            |
| Update role / activation / company of any user | `PUT  /api/v1/admin/users/{user_id}`               |
| Hard-delete any user                        | `DELETE /api/v1/admin/users/{user_id}`                |
| Create a new tenant (company)               | `POST /api/v1/admin/companies`                        |
| List companies w/ aggregates                | `GET  /api/v1/admin/companies`                        |
| Delete a company (cascades products + queries) | `DELETE /api/v1/admin/companies/{cid}`             |
| Audit log feed (stub)                       | `GET  /api/v1/admin/audit-logs`                       |
| LLM / RAG diagnostics (stub)                | `GET  /api/v1/admin/neural-diagnostics`               |
| Toggle `companies.admin_suspended`          | *(not yet exposed — direct DB only)*                  |
| All endpoints reachable by 👤 (e.g. `/auth/me`) | inherited                                          |

**Admin lifecycle rules:**
- An Admin row that's set `is_active=False` cannot log in (401/403 chain).
- Deleting an Admin is unrestricted — be careful not to delete the **last** Admin (no safeguard exists).
- Admins are **not bound** to a `company_id`. The field is allowed to remain `NULL`.

### Auth mechanics

- `POST /auth/login` (OAuth2 password flow) returns a JWT signed `HS256` with `SECRET_KEY`, subject = email, 1-week expiry (`ACCESS_TOKEN_EXPIRE_MINUTES = 60*24*7`).
- `Authorization: Bearer <token>` decoded by `deps.get_current_user`, then chained guards enforce role.
- Password-reset tokens are a separate short-lived JWT minted by `security.generate_password_reset_token`.

## 5. Request Lifecycles (Critical Flows)

### 5.1 Inbound customer query (RAG pipeline)

1. Google Apps Script attached to a Sheet posts to `POST /api/v1/webhook/google-forms` with `{ company_id (hashed), complainant_email, query_text, complaint_id? }`.
2. Backend looks up `Company` by hashed ID, pulls first product's `manual_content`.
3. `rag_service.generate_ai_answer` builds an in-memory `VectorStoreIndex` from the manual, queries it via Groq Llama-3-70B with a professional sales-rep prompt; on failure, returns a template fallback.
4. New `Query` row is persisted (`status = Pending`, `ai_generated_answer` populated, `complaint_id` generated if missing).
5. Resend email goes straight to the complainant with the AI-drafted reply.
6. The query is now eligible for SalesRep assignment (FCFS — first rep to act picks it up via PATCH).

### 5.2 Escalation / negotiation flow

1. SalesRep calls `POST /sales/queries/{id}/escalate` with `{ reason, priority }`.
2. Backend sets `is_escalated = True`, `status = Escalated`, computes `deadline_at` (12 h for `high`, 48 h for `normal`), and sends an HTML email to the company Owner.
3. Owner sees the item in `GET /owner/negotiations`, resolves via `POST /owner/negotiations/{id}/resolve` with `{ final_answer, status }`.
4. Customer receives an "Official Response" email; query is marked `Resolved` and stamped with `resolved_at`.

### 5.3 Document upload → RAG corpus

1. Owner uploads a PDF or image to `POST /owner/products/{id}/upload`.
2. Backend uses **PyMuPDF** to extract per-page text. Pages with <50 chars of text (likely scanned) are rasterised and sent to a local **Ollama** vision-language model for OCR; raw images go straight to Ollama.
3. Extracted text saved as a `ProductDocument` row; the parent `Product.manual_content` is **rebuilt** by concatenating all docs, ensuring RAG always sees the current corpus.
4. `ActivityLog` row written for audit.

### 5.4 Discount application

1. SalesRep calls `POST /sales/queries/{id}/apply-discount` with `{ product_id, discount_pct }`.
2. Backend caps `discount_pct` at the product's `max_discount_pct`, computes a discounted price from `price` (or `base_price/100`), and writes a templated `final_answer`.
3. If the request exceeded the cap, the reply notes that the rep should escalate to the Owner for further reduction.

## 7. Cross-Cutting Concerns

- **CORS:** Wide-open (`allow_origins=["*"]`) — fine for dev, must be tightened for prod.
- **Error handling:** A global `Exception` handler in `main.py` dumps `traceback.format_exc()` to `error.txt` and returns `500 {message: str(exc)}`.
- **Schema evolution:** No Alembic. Instead, `ensure_company_columns()` runs at startup to `ALTER TABLE` add missing columns for backward-compatibility; standalone scripts (`migrate_statuses.py`, `migrate_theme.py`) patch existing DBs.
- **Audit trail:** `ActivityLog` table — Owner endpoints write entries for product/document lifecycle events.
- **Themes:** `User.theme` (`system | dark | white`) — frontend toggles body class accordingly.

### 10.6 Triple-lock suspension

Effective company activity becomes:
```
is_active = NOT billing_suspended
            AND NOT (admin_suspended AND manager_suspended)
```

Billing's suspension is unilateral (one flag fires the lock); Admin + Manager remain a dual-lock pair.

### 10.7 Discount ceiling cascade (canonical)

```
Agent ceiling = product.max_discount_pct
Manager ceiling = companies.config.manager.manager_discount_ceiling
Owner   ceiling = unlimited (subject to business policy)
```

Above ceiling at any tier → `DiscountApproval` row → escalates to the next tier (Manager or Owner negotiation).

### 10.8 RAG with persistence (replacing per-request rebuild)

Today's `rag_service.generate_ai_answer(query, manual)` is replaced with:

```python
async def generate_ai_answer(
    *, company_id: str, product_id: str | None, query_text: str,
) -> tuple[str, int]:
    # retrieve top-k from per-tenant collection,
    # optionally rerank via RetrievalJudge online step,
    # call Groq with grounded prompt + numbered chunks,
    # return (answer, tokens_used)
```

Per-tenant collection name: `tenant_<company_id>`. Re-index triggers: doc upload/delete (Owner/Curator), `Product.manual_content` direct edits, product/company deletion, manual Admin re-index.

### 10.9 Deployment target

- **Backend**: Postgres (+ pgvector optional) instead of SQLite; Uvicorn workers behind Gunicorn/Nginx; secrets via env / secret manager; containerised.
- **Frontend**: Next.js on Vercel or self-hosted Node; `revalidateTag` for cache busts.
- **Vector store**: Qdrant (managed or self-hosted) in prod; Chroma local for dev.
- **Email**: Resend outbound + Resend Inbound (or Postmark / SES) for inbound parser.
- **Real-time**: WebSocket (FastAPI WebSocket route) or SSE for chat rooms + queue updates.
- **Observability**: structured JSON logs (`structlog`), request_id middleware, optional OpenTelemetry export.
- **CI**: pytest + Playwright smoke; Alembic upgrade dry-run on a copy of prod before each deploy.
